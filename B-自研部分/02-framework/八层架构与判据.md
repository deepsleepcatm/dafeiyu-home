# 我这套系统的底层架构 · 谁是谁 · 怎么判断

2026-11-24　组A
**这份不是设计图，是此刻真实跑着的东西。** 每一层都标了：在哪、谁管、坏了怎么看出来。

---

> **路径说明**：本文里的路径都是**示例**。`<工作区>`、`<DSH主目录>`、`<安装位置>`
> 都要换成你自己的实际位置 —— 你装在哪，就写哪。

# 一、先给判断方法

排任何问题，按这个顺序问，**不要跳层**：

```
1. 它「是什么层」的问题？
2. 那一层的「健康信号」是什么？
3. 信号不对 → 那一层坏了；信号正常 → 往上/往下找

最常见的方向错误：从最上层（对话不顺）开始查，查到最底层（Python 版本）才发现。
今天四次全是这个形状，所以判断顺序要从下往上。
```

**从下往上**：L0 硬件 → L1 运行时 → L2 DSH → L3 服务 → L4 外部 → L5 数据 → L6 组 → L7 判据

# 二、八层，一层一层说

## L0 · 硬件与系统

**是什么**：这台笔记本（Windows）
**关键约束**：
- Smart App Control 是开启的（`VerifiedAndReputablePolicyState = 1`），会拦未签名程序
- Windows Terminal 是默认控制台，每次 spawn 都闪窗（会影响语音识别）

**坏了怎么看出**：所有命令都"能跑但结果怪" → 先怀疑策略/权限，不是代码

## L1 · 运行时（四个解释器，各有各的用）

| 路径 | 版本 | 谁在用 | 不能用它做什么 |
|---|---|---|---|
| `C:\...\node\24.22.1\node.exe` | v24.22.1 | 桥、DSH、所有 .mjs | — |
| `C:\...\dsh-runtimes\...\python.exe` | **3.12.14** | mem-tools、链路上的 python 脚本 | 缺 onnxruntime（那是 mem-tools 自带的） |
| `C:\...\Python310\python.exe` | **3.10.6** | **playwright**（只有它装了 + chromium 内核） | 跑不了 mem-tools（cp312 的 pyd） |
| `bili-duty\.venv\Scripts\python.exe` | 3.12.15 | **B站插件、qzone-sdk、faster-whisper** | 写不了文件（权限） |
| `bili-duty\uv-python\...\python.exe` | 3.12.15 | 曾用于 B站（**现在是空壳，只有 pip**） | 什么都做不了 |

**这是最容易出错的一层。** 今天炸了两次：
- mem-tools 用 3.10 跑 → numpy cp312 pyd 加载失败，报在 `numpy._core`
- B站插件指向 uv-python 空壳 → import mcp 失败

**健康判据**：
```
node --version                      → v24.22.1
<3.12> -c "import numpy;print(1)"   → 1        （mem-tools 靠它）
<3.10> -c "import playwright;print(1)" → 1     （pwcli 靠它）
<venv> -c "import mcp,bilibili_api;print(1)" → 1  （B站插件靠它）
```

**判据的核心**：**"文件存在" ≠ "能干活"**。要看实际 import 成不成。

## L2 · DSH 本体 + profile

**是什么**：`DeepSeek Harness.exe`（29 个进程，正常，Electron 多进程）
**在哪**：装 `<安装位置>\AppData\Local\Programs\DeepSeek Harness`，profile 在 `<DSH主目录>\profiles\<你的profile名>`
**谁管**：`package.json` 的 `dsh.profile.bundles`（29 个）+ `cordis.patch.yml`

**关键特性（每天会变的东西）**：
- **API 端口每次重启都变**（现在 `63371`）
- 会话数据在 `storages\session_projcache\sessions\`（502 MB）
- 插件可以是 `npm` / `github:` / `codeload` / **`file:` / `link:`** 五种来源
  - 前三种别人能装，**后两种只在本机能用**

**坏了怎么看出**：
```
端口通不通                  Test-NetConnection 127.0.0.1 -Port 63371
插件加载成不成              plugin_manager list_bundles（看 error 字段）
界面渲不渲染                开窗口看一眼，别只看 API
```

**今天在这里踩的坑**：`dsh-vision-toolkit` 版本不兼容（要求 DSH < 0.2.0，我们 0.2.2-rc.5）→ 装了但永远 disabled

## L6 · 组层（19 个会话）

**是什么**：19 个 DSH 会话，每个组一个，各有 session id
**谁管**：`bridge-state.json` 的 `sessions` 映射（17 个有 id）
**谁拉起**：`chat-bridge.mjs` 通过 DSH API 唤醒

**健康判据**：
```
会话文件存在        storages\session_projcache\sessions\<sid>.json
48 小时内动过       看 mtime
★ 被唤醒后真回话 ★  群聊里能看到它发言
```

**今天最大的坑**：11:20 组C按"目录时间戳"删了 86 个会话，其中 5 个组的在用的也被删。
教训：**目录 mtime 会被写入刷新、被恢复重置，不能用来判断"这活还在不在"**。要看目录内 `session.v4.jsonl.zstd` 的 mtime。

# 四、排障的正确顺序（今天总结的）

**从下往上，每层先看健康信号，别跳层。**

| 现象 | 先查哪层 | 判据 |
|---|---|---|
| 所有命令都怪 | L1 运行时 | 用的是哪个解释器 |
| 某个工具报看不懂的错 | L1 运行时 | 版本/权限，不是业务代码 |
| 插件装了不生效 | L2 DSH | 版本兼不兼容 |
| 消息进得来没人回 | L3 服务 → L7 判据 | 桥进程 + trace |
| QQ/微信断了 | L4 外部 | SnowLuma 端口 / ClawBot |
| 记不住事 | L5 数据 | 记忆库有没有写进去 |
| 某组不说话 | L6 组 | 会话文件 + 唤醒记录 |
| 不知道发生了什么 | L7 判据 | trace / 日志 |

# 五、这套架构的短板（老实说）

1. **四套数据互不通**（L5）—— 记忆、事件、灵魂、群聊各存各的，没有统一查询入口
2. **L3 的"活着"判据刚建立**（日志重定向今天才修）—— 之前的故障全部无法追溯
3. **L4 的 SnowLuma 自愈代码是坏的** —— 检测到了但拉不起来，已发现未修
4. **L6 没有任何删除保护** —— 11:20 那次事故就是没有拦截机制
5. **L1 四个解释器没有统一入口** —— 每次都要人工判断该用哪个
